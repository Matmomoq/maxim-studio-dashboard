# Доработки и задачи

Для разработчика заказчика: используйте Issues приватного репозитория, если команда выберет этот процесс. Шаблоны «Доработка» и «Ошибка» уже включены; сами задачи этим экспортом не создаются. Синхронизации с Asana нет; внутреннее планирование владельца остаётся в его личном пространстве Asana.

В задаче укажите экран/показатель, проблему, пример, ожидаемый результат, дату события, фильтры и критерии приёмки. Приложите только обезличенные данные. Различайте просьбу уточнить бизнес-правило и техническую ошибку.

## Рабочий цикл

1. Создать ветку от main для конкретной задачи.
2. Найти модуль по docs/ARCHITECTURE.md и проверить существующие правила/тесты.
3. Для изменения вычислений добавить пример и регрессионный тест; для схемы — отдельную миграцию.
4. Выполнить `python -m unittest test_dashboard test_amocrm_loader test_security -q`.
5. Проверить затронутые экраны/API на тестовом окружении, включая фильтры и экспорт.
6. Создать PR: что изменилось, какое бизнес-правило согласовано, как проверено, нужна ли миграция/настройка, как откатить.

Не смешивать рефакторинг расчётов с изменением бизнес-правил без явного описания. Не менять чужие текущие данные для проверки форм. Мерж не означает публикацию: релиз выполняется отдельно.
